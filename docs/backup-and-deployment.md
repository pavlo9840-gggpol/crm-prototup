# Резервні копії та безпечне оновлення АвтоЗапас

Цей документ описує поточну поведінку та безпечний порядок експлуатації. Це не підтвердження, що відновлення вже перевірено на робочій інсталяції.

## Що зараз робить застосунок

- Сторінка `/backup/` доступна лише користувачу з `is_superuser=True`.
- Архів містить знімок SQLite (`db.sqlite3`) і файли з `MEDIA_ROOT`, якщо каталог медіа існує.
- Знімок БД створюється через SQLite `VACUUM INTO`.
- Ручне збереження залишає до 14 останніх архівів; список сторінки показує до 30.
- Завантаження наявного архіву перевіряє ім'я за шаблоном `backup-YYYYMMDD-HHMMSS.zip`.
- Поточна реалізація резервного копіювання не підтримує PostgreSQL та інші рушії БД.

## Обмеження, які треба врахувати

- Каталог `backups/` розташований у дереві проєкту. Це не окрема копія на іншому диску чи сервері.
- Архіви не шифруються автоматично. Доступ до каталогу й завантажених копій має бути обмежений.
- Знімок БД узгоджений на момент створення, але процедуру відновлення медіафайлів оператор виконує окремо.
- Не можна вважати резервну копію надійною, доки архів не перевірено та не виконано тестове відновлення.
- Конфігурація production вимагає `DJANGO_SECRET_KEY` і непорожній `DJANGO_ALLOWED_HOSTS`, коли `DJANGO_DEBUG=0`. Для локальної інсталяції задайте також `AUTOZAPAZ_LICENSE_PUBLIC_KEY`.

## Перед оновленням

1. Зупиніть запис нових операцій на час обслуговування або погодьте коротке вікно простою.
2. Створіть резервну копію через сторінку адміністратора або окрему перевірену процедуру.
3. Переконайтеся, що ZIP відкривається, містить `db.sqlite3` і очікувані файли `media/`.
4. Збережіть ще одну копію архіву поза каталогом проєкту — на іншому диску або контрольованому віддаленому сховищі.
5. Зробіть копію поточної інсталяції та зафіксуйте поточний commit перед розгортанням.
6. Перевірте міграції на копії бази, а не вперше на єдиній робочій базі.
7. Після оновлення виконайте `python manage.py check` і ключові сценарії продажу, повернення, руху складу та приймання.

## Тестове відновлення SQLite

Виконуйте на окремій копії проєкту, не на робочій базі.

1. Зупиніть тестовий екземпляр Django.
2. Розпакуйте архів у тимчасовий каталог.
3. Переконайтеся, що в ньому є `db.sqlite3`; перевірте ZIP командою `unzip -t backup-YYYYMMDD-HHMMSS.zip`.
4. Підставте копію БД у тестове середовище й відновіть вміст `media/` до тестового `MEDIA_ROOT`.
5. Запустіть `python manage.py check`, потім `python manage.py test core.tests_financial_integrity core.tests_access_control`.
6. Увійдіть тестовим адміністратором і перевірте наявність ключових товарів, продажів, приймань і завантажених файлів.
7. Зафіксуйте дату, commit, розмір архіву та результат.

## Критерії готовності до production

- [ ] Секрети та `SECRET_KEY` надходять із змінних середовища або менеджера секретів.
- [ ] `DEBUG=False`, а `ALLOWED_HOSTS` містить лише потрібні домени.
- [ ] HTTPS, secure cookies і CSRF trusted origins налаштовані під фактичний домен.
- [ ] Резервні копії копіюються поза сервером застосунку й мають контроль доступу.
- [ ] Відновлення перевірене на окремому середовищі.
- [ ] Для обраної БД існує підтримуваний backup/restore-процес; поточний вбудований механізм працює лише із SQLite.
- [ ] Визначено відповідального за оновлення, контроль архівів і регулярний тест відновлення.


## Перевірка та нормалізація старої бази до одного локального магазину

Додано команду `migrate_to_local_store`. За замовчуванням вона працює **лише для читання** та нічого не змінює.

### 1. Спочатку зробіть аудит

Зупиніть вебзастосунок або переведіть його в режим обслуговування, щоб під час перевірки не створювалися нові документи. У каталозі проєкту виконайте:

```bash
python manage.py migrate_to_local_store
python manage.py migrate_to_local_store --json
```

Звіт показує:
- кількість локальних магазинів та їхніх власників;
- кількість записів у кожній моделі, яка має зв'язок із магазином;
- записи без `company_id`, які можуть бути прив'язані до єдиного магазину;
- активних користувачів без ролі;
- посилання між об'єктами різних магазинів;
- конфлікти унікальності, які виникнуть при перенесенні (телефони клієнтів, штрихкоди, шаблони, плани оплати та інші обмежені ключі).

### 2. Застосування дозволене лише після чистого аудиту

Команда відмовляється працювати, якщо в базі кілька магазинів, є неоднозначний власник, активні працівники без ролей, міжмагазинні посилання або конфлікти унікальності. Вона не видаляє записи та не намагається самостійно зливати дублікати.

Для SQLite, після окремого перевіреного резервного копіювання і зупинки застосунку:

```bash
python manage.py migrate_to_local_store \
  --apply \
  --backup /шлях/поза/проєктом/autozapaz-before-local-store.sqlite3
```

Прапорець `--apply` обов'язковий для запису. `--backup` має вказувати на новий файл, якого ще не існує. Команда створює SQLite backup через узгоджений механізм backup API, перевіряє `PRAGMA integrity_check`, і лише потім у транзакції заповнює порожні `company_id` єдиним магазином. Якщо в старої бази немає запису магазину й є рівно один активний звичайний користувач, команда створює локальний магазин і роль власника. Якщо активних працівників декілька, команда зупиняється: їхні ролі потрібно визначити явно.

Застосування наразі підтримується тільки для SQLite. PostgreSQL потребуватиме окремої процедури backup/restore та перевірки перед записом.

### 3. Якщо знайдено кілька магазинів

Не видаляйте таблицю `Company`, не запускайте SQL на кшталт `UPDATE ... SET company_id = 1` і не змінюйте зовнішні ключі вручну. Звіт навмисно блокує автоматичне злиття: перед ним потрібне окреме зіставлення дублікатів товарів/клієнтів, конфліктів штрихкодів і телефонів, шаблонів документів, планів оплати, власників та ролей. Для такого випадку потрібно підготувати окремий план перенесення з попереднім dry-run і таблицею рішень.

### Межі цього етапу

Цей інструмент нормалізує дані до **одного запису локального магазину**, але поки не видаляє модель `Company`, `CompanyMembership` чи зовнішні ключі з операційних таблиць. Вони залишені для сумісності та цілісності старих документів. Фізичне спрощення схеми БД буде окремою міграцією після аудиту всіх запитів і підтвердженого перенесення старих інсталяцій.

## Новий формат резервної копії та перевірка перед відновленням

Нові архіви містять:
- `db.sqlite3` — узгоджений SQLite snapshot;
- `media/` — копії завантажених файлів (символічні посилання пропускаються);
- `manifest.json` — версію формату, час створення, розмір і SHA-256 кожного файлу;
- `README.txt` — коротку інструкцію.

Під час створення архіву застосунок виконує `PRAGMA integrity_check`, формує ZIP, а потім повторно перевіряє ZIP, маніфест і контрольні суми. Запис у `backups/` виконується через тимчасовий файл та атомарне перейменування. Старі архіви видаляються лише після успішного створення й перевірки нового.

Перед ручним відновленням перевірте архів:

```bash
python manage.py verify_backup /шлях/до/backup-YYYYMMDD-HHMMSS.zip
```

Команда нічого не змінює в робочій базі: перевіряє структуру ZIP, небезпечні шляхи, контрольні суми (якщо є маніфест) і SQLite integrity у тимчасовій копії. Старі ZIP без `manifest.json` також підтримуються, але для них доступна лише перевірка ZIP і SQLite integrity.

Щоб зберігати резервні копії поза каталогом програми, задайте `AUTOZAPAZ_BACKUP_DIR` абсолютним шляхом до каталогу з обмеженим доступом. Наприклад, на Linux — окремий каталог у `/var/backups/autozapaz`, на Windows — окремий каталог на диску резервного копіювання. Переконайтеся, що користувач служби має право запису.

**Важливо:** `verify_backup` — це перевірка архіву, а не автоматичне відновлення. Не розпаковуйте архів поверх робочої інсталяції без зупинки застосунку, окремої копії поточної БД і перевіреного плану відкату. Повноцінний автоматизований restore workflow і перевірка на копії реальної клієнтської БД залишаються окремими задачами.

## Ізольоване тестове відновлення

Для перевірки відновлення без ризику перезаписати робочу БД використовуйте команду, яка створює новий каталог і відмовляється працювати, якщо він уже існує:

```bash
python manage.py restore_backup /шлях/до/backup-YYYYMMDD-HHMMSS.zip /шлях/до/autozapaz-restore-test --apply
```

Команда спочатку перевіряє ZIP, маніфест і SQLite integrity, потім відновлює `db.sqlite3` та `media/` у тимчасовий каталог поруч із цільовим і атомарно перейменовує його. Символічні посилання й небезпечні шляхи в архіві заборонені. Без `--apply` команда нічого не створює. Вона **не** змінює налаштування Django, активну базу або `MEDIA_ROOT`.

Після команди можна налаштувати окремий тестовий екземпляр програми на відновлені файли й перевірити логін, товари, продажі, складські рухи та документи. Не запускайте тестовий екземпляр на бойовій базі й не вказуйте бойовий каталог як ціль відновлення.

## Каталог даних окремо від програми

Поточна конфігурація зберігає дані поза директорією з кодом:
- `AUTOZAPAZ_DATA_DIR` — каталог SQLite та медіафайлів. Якщо змінну не задано, використовується системний каталог користувацьких даних через platformdirs (Linux: `~/.local/share/AutoZapaz`; Windows: `%LOCALAPPDATA%\\AutoZapaz`).
- `AUTOZAPAZ_BACKUP_DIR` — окремий каталог резервних копій; типовий шлях `<AUTOZAPAZ_DATA_DIR>/backups`.
- `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS` і `AUTOZAPAZ_LICENSE_PUBLIC_KEY` задають production-конфігурацію.
- Статичні файли збираються в `staticfiles/` у каталозі релізу та віддаються WhiteNoise; локальний сервер запускається командою `python manage.py serve` через Waitress.

### Перенесення зі старого розміщення

Якщо стара інсталяція зберігала `db.sqlite3`, `media/` і `backups/` поруч із `manage.py`, порядок переходу такий:

1. Зупинити вебсервер і переконатися, що немає інших процесів, які пишуть у стару БД.
2. Оновити файли програми та встановити залежності, але **не запускати сайт і не виконувати `migrate` до копіювання старої БД**.
3. Запустити `python manage.py migrate_local_data` — це read-only аудит плану.
4. Перевірити виведені шляхи й виконати `python manage.py migrate_local_data --apply`.
5. Команда створює копії SQLite через SQLite backup API, перевіряє `PRAGMA integrity_check`, копіює медіафайли й старі резервні копії, відмовляється перезаписувати наявні цільові дані та залишає оригінали недоторканими.
6. Лише після успішного копіювання виконати `python manage.py migrate`, запустити `python manage.py serve` і перевірити логін, товари, продажі, документи та зображення.
7. Не видаляти старі файли вручну, доки не створено нову резервну копію й не перевірено відновлення.

Якщо в новому каталозі вже існує `db.sqlite3`, команда зупиняється і нічого не перезаписує. У такому разі не видаляйте файл навмання: спочатку визначте, чи це вже створена нова база, і зробіть окрему резервну копію.

### Локальний сервер

`python manage.py serve --host 127.0.0.1 --port 8000` запускає WSGI через Waitress без Django autoreload. Типова адреса доступна лише на цьому ПК. Не використовуйте `--host 0.0.0.0` для SQLite-інсталяції: підтримка спільної роботи через LAN потребує окремо налаштованої PostgreSQL-бази, мережевих правил і служби БД.
