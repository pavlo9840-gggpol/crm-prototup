# Linux updater: аварійне відновлення

Цей документ описує безпечні дії після аварійного переривання
`deploy/linux/update.sh`. Він **не є автоматичним recovery-скриптом**.
Поки існує `/var/lib/autozapaz-update-state.json`, повторний запуск updater
навмисно заблокований.

## Важливі правила

- Не видаляйте журнал стану, щоб «розблокувати» оновлення.
- Не запускайте updater повторно і не запускайте нові міграції.
- Не видаляйте каталоги `.rollback-restore-*`, `*.failed-*`, старі релізи,
  резервні копії або файли SQLite `-wal` / `-shm`.
- Не копіюйте окремо `db.sqlite3`, поки існують `db.sqlite3-wal` та
  `db.sqlite3-shm`: це може втратити підтверджені транзакції.
- Не запускайте службу, якщо невідомо, яка версія коду відповідає поточній
  схемі БД.
- Відновлення має виконувати адміністратор із резервною копією поза сервером.
  Якщо немає впевненості в цілісності БД, збережіть стан і передайте діагностику
  розробнику/підтримці.

## 1. Зібрати діагностику без змін даних

Виконайте команди від root або через `sudo`:

```bash
sudo systemctl status autozapaz.service --no-pager
sudo journalctl -u autozapaz.service -n 200 --no-pager
sudo stat /var/lib/autozapaz-update-state.json
sudo cat /var/lib/autozapaz-update-state.json
sudo readlink -f /opt/autozapaz/app
sudo readlink -f /opt/autozapaz/venv
sudo ls -lah /opt/autozapaz/releases /opt/autozapaz/venvs
sudo find /var/lib/autozapaz -maxdepth 2 -mindepth 1 -printf '%M %u:%g %p\\n'
sudo ls -lah /var/lib/autozapaz/backups
```

Збережіть вивід, точний час переривання та commit/версію релізу, який
намагалися встановити. Не публікуйте вивід конфігурації
`/etc/autozapaz/autozapaz.env`: він містить секрети.

## 2. Інтерпретація журналу

Поле `phase` показує останню успішно записану фазу, а не гарантує, що
наступна операція не встигла частково виконатися. Зокрема, живлення може
зникнути між файловою операцією та наступним записом журналу.

| Фаза | Що потрібно звірити |
|---|---|
| `preparing_release` | Чинні посилання app/venv; чи залишилися неповні каталоги нового релізу |
| `service_stopped` | Чи зупинена служба; чи створено backup |
| `backup_created` | Наявність, власник і цілісність backup; наявність restore-каталогу |
| `rollback_ready` | Наявність перевірених `restore_dir/db.sqlite3` і `restore_dir/media` |
| `app_switched` | Чи вказує app на старий або новий реліз; чи не змінилося venv |
| `venv_switched` | Чи узгоджені app і venv з однією версією |
| `migrations_started` | Чи могли міграції змінити схему; не запускати старий код без перевіреного відкату |
| `health_check_passed` | Перевірити фактичний стан служби, HTTP health-check і відповідність app/venv |

Журнал є контрольним орієнтиром, а не доказом завершення файлової операції.
Звіряйте фактичні шляхи, каталоги та вміст backup перед будь-якою зміною.

## 3. Підготувати безпечне відновлення

1. Якщо служба активна, не зупиняйте її автоматично лише за назвою фази:
   спочатку визначте, чи обслуговує вона запити та чи відповідає код поточній БД.
2. Якщо служба зупинена, залиште її зупиненою до завершення перевірки.
3. Зробіть копію всього каталогу `/var/lib/autozapaz` на окремий носій,
   зберігаючи власників, права, SQLite DB/WAL/SHM, media, backup та всі
   `.rollback-restore-*` / `*.failed-*` каталоги. Не змінюйте оригінал.
4. Перевірте резервний архів штатною командою `verify_backup` з тієї версії
   програми, якою його створено. Переконайтеся, що архів читається та містить
   БД і media.
5. Визначте одну узгоджену пару попереднього app і venv. Не покладайтеся лише
   на імена каталогів або поле `phase`.
6. Відновлюйте БД і media лише з однієї перевіреної точки backup/restore.
   Не змішуйте файли з різних резервних копій.
7. Після відновлення перевірте SQLite integrity, Django system check,
   міграції без застосування (`migrate --plan`), авторизацію та контрольні
   документи/залишки. Лише після цього запускайте службу та перевіряйте HTTP.

## 4. Завершення інциденту

Журнал можна прибрати лише після того, як адміністратор підтвердив:
- код і venv узгоджені;
- база даних та media відновлені або підтверджено, що вони не змінювалися;
- backup перевірений і збережений поза сервером;
- служба проходить health-check;
- є копія діагностики та опис виконаних дій.

Не видаляйте журнал вручну як спосіб обходу блокування. Після recovery
потрібно окремо перевірити, що наступне оновлення має більший підписаний
`release_sequence` і запускається з чистого стану.

## Поточне обмеження

Поточний updater має durable journal, взаємне блокування та fail-closed
поведінку, але не має автоматичного відновлення після аварійного завершення.
Поки recovery helper та crash-injection acceptance не реалізовані й не
перевірені на окремій VM, Linux updater не можна вважати повністю прийнятим
для комерційного production використання.
