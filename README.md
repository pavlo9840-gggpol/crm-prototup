# Django — система для роздрібного магазину

## Запуск
    python -m venv venv && source venv/bin/activate    # Windows: venv\Scripts\activate
    pip install -r requirements.txt
    python manage.py migrate
    python manage.py seed_demo        # демо: admin/admin123, cashier/cashier123, товар «Кола 0.5л»
    python manage.py runserver
Відкрити http://127.0.0.1:8000/

## Встановлення
    pip install -r requirements.txt     # Django, Pillow, ReportLab (PDF), PyMuPDF (PNG/JPG, необов'язково)

## Ролі
- Адміністратор = користувач з прапорцем «staff» (повний доступ).
- Касир = звичайний користувач без «staff» (створюється в /admin/): лише каса, власні продажі, зміни.

## Тести (сценарій приймання з ТЗ)

## Версія 3: дизайнер бланків (розділ 9 ТЗ)
- **Меню:** підпункти бічного меню згортаються/розгортаються (стан запам'ятовується; група з активною сторінкою відкрита).
- **Дизайнер** (`/designer/`): візуальний редактор — перетягування мишкою, зміна розміру, прив'язка до сітки,
  вирівнювання, групування, копіювання/вставка, відміна/повтор (Ctrl+Z / Ctrl+Y), шари, масштаб.
  Розміри: A4, A5, чек 58/80 мм, цінник, довільний. Елементи: текст, поля даних, таблиця, зображення (логотип,
  печатка, підпис), лінія, рамка, штрих-код (Code128), QR-код, підсумковий рядок.
- **Умови:** показати елемент, якщо…; виділити жирним, якщо… (порожнє, =, ≠, >, ≥, <, ≤, містить);
  «якщо порожнє» → показати / сховати / прочерк; елемент з прапорцем ↕ розтягується, а нижні зсуваються.
- **Таблиці** автоматично переходять на нові сторінки (шапка повторюється, підсумки — на останній).
- **Типи документів:** касовий чек, видаткова накладна, прихідна накладна, акт списання, звіт про залишки,
  звіт про рух товарів, цінник.
- **Бібліотека:** стандартні шаблони (не редагуються, оновлюються разом із програмою), власні (ніколи не
  перезаписуються), копіювання, «зберегти як новий», шаблон за замовчуванням, експорт/імпорт JSON і ZIP-резерв.
  Імпорт завжди створює копію; для старої версії формату показується попередження.
- **Друк:** перегляд, друк, PDF, PNG/JPG, груповий друк (галочки в списках продажів, закупівель, товарів, списань),
  вибір шаблону під час друку, кнопка «Дизайнер» у вікні друку. Чек також як TXT для термопринтерів.
- **Автодрук чека** (Налаштування → Фірма): вимкнено / браузерний друк / PDF. Ставка ПДВ береться з налаштувань фірми.
- Шаблони зберігаються в базі даних, тому входять у резервну копію БД (`db.sqlite3`).

Не реалізовано: інтеграція з ПРРО/фіскальними реєстраторами, імпорт шаблонів УкрСклад (FastReport), скрипти й макроси
(за ТЗ не входять до початкової версії).

## Версія 5: товар під замовлення від постачальників (минає склад)

**Ідея.** Прайс постачальника (Excel) завантажується у «віртуальний каталог» і не створює складських залишків.
Менеджер знаходить позицію на касі за артикулом і продає її. Склад при цьому не чіпається. Коли товар прийшов,
натискається «Прибув» (запускається відлік на забір, типово 14 днів), далі або «Видано клієнту» (товар минув склад),
або, якщо клієнт не забрав, «На склад» чи «Повернути постачальнику».

| Розділ меню | Що робить |
|---|---|
| Склад → Прайси постачальників | Імпорт .xlsx/.csv: вибір колонок (артикул, бренд, назва, ціна, наявність), повторний імпорт оновлює ціни, зниклі позиції стають «немає в наявності» |
| Склад → Аналоги (кроси) | Пари артикулів-аналогів (вручну або з файлу з двох колонок). Працюють в обидва боки і через ланцюжок |
| Склад → Націнки клієнтів | Довідник націнок (напр. Роздріб +30 %, СТО +15 %). Націнку призначають у картці клієнта, одна може бути типовою |
| Торгівля → Замовлення в дорозі | Усі позиції під замовлення, список «що замовити» по постачальниках, відлік днів, дії над позицією |
| Торгівля → Продажі менеджерів і маржа | Що, кому, за яку ціну продав кожен менеджер, закупівля, маржа в грн і %, підсумки по менеджерах, експорт CSV. Менеджер бачить лише свої продажі |

**Каса.** Пошук без штрихкодів: артикул порівнюється без пробілів і дефісів (`19-152615` = `19152615`). Результат у трьох блоках:
«На складі», «Аналоги, що вже є на складі», «У постачальників». Для позиції постачальника ціна = закупівельна + націнка клієнта;
її можна змінити списком націнок або ввести вручну, маржа під рядком оновлюється одразу.

**Облік.**
- Позиція постачальника не змінює залишок складу. Для неї створюється технічна картка товару (залишок 0), яка не показується
  на касі, доки товар не оприбутковано.
- «На склад»: товар оприбутковується (рух «Оприбутковано: клієнт не забрав»), позиція в чеку скасовується як повернення клієнту.
  Закупівельна ціна картки береться з цієї партії, якщо до цього товару на складі не було.
- «Повернути постачальнику»: склад не змінюється, позиція в чеку скасовується.
- Повернення чека з ще не виданою позицією під замовлення не створює «фантомного» залишку.
- Грошові розрахунки з клієнтом при скасуванні (повернення коштів) облік повернень ведеться як і раніше, окремо від каси.

Нові тести: `python manage.py test core.tests_transit`.

## Версія 6: бренди в картці товару та підключення API постачальників

**Бренд + артикул.** Товар однозначно визначається парою «бренд + артикул» (однаковий артикул у різних виробників це різні товари).
- Форма товару: спершу «Бренд» (обов'язковий, з підказками зі складу і прайсів), потім «Артикул», «Назва». Бренд зберігається у верхньому регістрі, дублікат пари бренд + артикул відхиляється (артикули порівнюються без пробілів і дефісів).
- Список товарів: колонки «Бренд» і «Артикул», пошук за брендом та артикулом у будь-якому написанні.
- CSV: нова колонка «Бренд». Товар шукається за парою бренд + код, а без колонки бренду за артикулом, якщо він однозначний.
- Каса: бренд видно у видачі та в чеку. Якщо артикул є в кількох брендів, Enter нічого не додає: менеджер обирає бренд сам.
- Після оновлення виконайте `python manage.py migrate`. Існуючим товарам бренд можна додати при редагуванні (форма вимагатиме його) або CSV-імпортом.

**API постачальника.** Склад → Прайси постачальників → «підключити API».
1. Вкажіть посилання, формат (JSON, XML або таблиця CSV/XLSX), спосіб передачі ключа і назви полів у відповіді (артикул, бренд, назва, ціна, залишок). Назви беруться з документації постачальника.
2. «Пробний запит» показує, як програма прочитала перші записи, нічого не записуючи.
3. «Оновити каталог зараз» записує весь каталог у прайс-списки (на склад він не потрапляє). Підтримується постраничне завантаження (параметр `page`).
4. Автоматично за розкладом: `python manage.py sync_prices` (cron або Планувальник завдань Windows). Ключ `--supplier ID` для одного постачальника.

Безпека: збережений ключ у формі не показується і не потрапляє в повідомлення про помилки; ключ можна не зберігати в базі, а вказати `env:НАЗВА_ЗМІННОЇ`. Адреси у внутрішній мережі заборонені. Порожня або «підозріло мала» відповідь не стирає наявний каталог (потрібна явна позначка). Зверніть увагу: ключ, збережений у базі, потрапляє в резервні копії бази.

Нові тести: `python manage.py test core.tests_brand_api`.

## Версія 7: аналоги за OE (як у TecDoc), картка запчастини, BM Parts

**Точні аналоги.** Деталі, привʼязані до одного OE-номера, вважаються взаємозамінними (принцип TecDoc). Рівні довіри:
«точний» (спільний OE), «підтверджено вручну», «кросс», «ймовірний» (лише ланцюжок кросів, потребує перевірки).
На касі аналоги видно з бейджем точності, а якщо ввести сам OE-номер, знайдуться всі деталі, привʼязані до нього.

**Картка запчастини** (посилання ℹ біля кожного результату пошуку): опис, характеристики, застосовність до авто, фото,
OE-номери, залишок на складі, ціни постачальників, таблиця аналогів зі спільними OE. Адміністратор може правити дані вручну.

**Звідки беруться OE-коди й описи** (прайс постачальника їх не містить):
1. API постачальника: окремий запит до картки кожної деталі (Склад → Прайси постачальників → налаштувати API, група 3).
   «Показати структуру картки» покаже реальну відповідь API, щоб вказати точні шляхи. Для всього каталогу:
   `python manage.py enrich_parts` за розкладом (за запуск до 2000 позицій, оброблені пропускаються).
2. Файли: Склад → «OE-номери та описи» (Бренд · Артикул · OE · Бренд OE; Бренд · Артикул · Опис · Характеристики · Застосовність).
3. Вручну в картці. Ручні правки API не перезаписує.

**BM Parts (Busmarket).** У налаштуваннях API є кнопка «Заповнити за шаблоном BM Parts»: прайс `POST /prices/list` (CSV із
двома рядками заголовків, залишки по складах підсумовуються), токен у заголовку `Authorization`, обовʼязковий `User-Agent`,
картка `GET /product/{id}?oe=full`. У тілі запиту треба вписати UUID валюти й складів, а токен видає менеджер BM Parts.
Шаблон складено за публічною документацією developer.bm.parts і перевірено на зразку їхнього CSV, але не на живому API.

Нові тести: `python manage.py test core.tests_parts`. Усього тестів: 71.

## Версія 9: автоаналоги з довірою, приймання накладної, авто клієнта, демо-база

**Аналоги без ручної роботи й безкоштовно.** Ліцензованої бази TecDoc немає, тому система збирає докази з кількох незалежних джерел і оцінює довіру 0-100%:
підтверджено вручну (100) · спільний OE-номер (70-90) · кросс з API постачальника (55) · кросс із файлу (45) · збіг за назвою: той самий тип деталі,
авто й позиція (до 40) · ланцюжок кросів (20). Що більше незалежних джерел збігається, то вища довіра. Менеджер у картці запчастини натискає ✓ (підтвердити)
або ✗ (не аналог: лише адміністратор), і система це запам'ятовує та ховає хибну пару з усіх джерел. Кроси з картки постачальника
підтягуються автоматично (група «3» в налаштуванні API, поле «де лежать аналоги»).

**Приймання накладної** (Торгівля → Приймання накладної). Завантажте Excel/CSV або вставте рядки. Система зіставляє кожен рядок за брендом і артикулом
(без пробілів і дефісів) із відкритими замовленнями клієнтів цього постачальника в порядку черги: позиції стають «Прибув» і запускається відлік на забір
(товар піде клієнту минаючи склад), а залишок оприбутковується на склад закупівлею. Якщо прийшло менше, ніж замовлено, позиція чека ділиться
(сума чека не змінюється). Перед застосуванням є перегляд «що куди піде»; ціна з накладної оновлює фактичну закупівельну; бачите попередження про
можливу заміну аналогом і про нові деталі. Повторне натискання безпечне. Усі приймання пишуться в журнал.

**Авто клієнта.** У картці клієнта (і прямо на касі кнопкою «＋ авто»): держномер, VIN (перевіряється формат), марка, модель, рік, двигун. Клієнта на касі
можна знайти за номером (латиницею чи кирилицею) або VIN. Авто зберігається в чеку, видно в замовленнях, історії менеджера й CSV. Якщо в картці деталі є
застосовність, каса підказує «✓ підходить до авто» або «? перевірте застосовність» (лише підказка: марки в каталозі й у картці клієнта можуть
бути записані по-різному, напр. «Renault» і «Рено»).

**Виправлення знайдені під час роботи.** У SQLite пошук по кирилиці не враховував регістр («амортизатор» не знаходив «Амортизатор»): це зачіпало пошук
товарів і клієнтів у вихідному коді; тепер працює для будь-якого регістру. Також виправлено формування артикула технічної картки товару постачальника.

**Демо-база для перевірки.** `python manage.py load_demo_data` створює вигадані дані: 2 постачальники, ~190 деталей з OE-звʼязками, описами й
застосовністю до авто, ~300 позицій у прайсах, клієнти з авто, 2 замовлення й тестову накладну `demo_invoice.csv`. Ці дані **не реальні**: артикули
й OE-номери вигадані. Видалити: `load_demo_data --reset`.

## Версія 10: правила цін, підбір за авто, зарплата менеджерів

**Правила цін** (Склад → Правила цін). Ціна = закупівельна + націнка, але не нижча за мінімальну маржу, з округленням вгору (до 1/5/10 ₴).
Найконкретніше правило перемагає: бренд + категорія → бренд → категорія → загальне (підкатегорія успадковує правило батьківської).
Націнка береться так: явна категорія цін клієнта (напр. СТО) → націнка правила → типова. Мінімальна маржа й округлення діють завжди.
Правила застосовуються на касі до позицій постачальників (та сама формула на сервері й у браузері; є тест на збіг), до товарів з «автоціною»
(при закупівлі, прийманні накладної й зміні прайсу постачальника) та в екрані **Перегляд цін**: де ціна нижча за правило, де маржа нижча за мінімум,
де закупівля в постачальника зросла; кнопки «застосувати до вибраних / до всіх проблемних», увімкнення автоціни. Там же журнал змін цін
постачальників за 14 днів. Автоціна рахується від найдешевшої доступної закупівлі в прайсах, а собівартість залишку не змінюється.

**Підбір за авто** (Торгівля → Підбір за авто; кнопка «🔧 підбір» на касі й у картці клієнта). Авто клієнта (марка, модель, рік) → сумісні деталі за даними
застосовності, згруповані за типом деталі, з наявністю на складі та цінами для цього клієнта з урахуванням правил. Враховуються роки випуску
(«2001-2014», «01-»). Потрібні дані застосовності: з API постачальника (група «3», поле «застосовність») або з файлу. Без них підбір порожній, і сторінка про це каже.

**Зарплата менеджерів** (Торгівля → Зарплата менеджерів; Плани оплати). Оплата = відсоток від маржі + фіксована частина на місяць (пропорційно днях). Є типовий
план і персональні. Маржа зараховується, коли товар видано: зі складу в момент чека, замовлений у постачальника коли клієнт його забрав (до цього він
«в дорозі» і окремо видимий). Повернення зменшують маржу; змінна частина не менше 0. Менеджер бачить свою комісію на сторінці «Мої продажі». CSV для бухгалтерії.
Зверніть увагу: відомість рахує за датою зарахування маржі, а «Продажі менеджерів» за датою чека. Це не помилка, а різні звіти.
